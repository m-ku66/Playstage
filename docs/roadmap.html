01Why this exists

The problem Playstage solves, and the shape of the solution.

Drawing backgrounds by hand for every panel is slow, and perspective consistency across a page is harder still. The standard fix is to block the environment out in 3D, then draw over a render. Blender can do this, but its workflow is built for finished assets: create a mesh, unwrap UVs, assign materials, manage a render pipeline. That is a lot of ceremony for "I need a street corner from three angles."

Playstage trades generality for speed. A small set of shapes, direct per-face texturing with no UV unwrapping, camera bookmarks you can flip between, and a one-click frame export.

Design principle

Every feature should shorten the path from "I need this background" to "I'm drawing over it." If a feature adds a step without removing two, it does not belong here.

What was picked, and what it was picked over.

DecisionChosenReasoning

RendererR3F + Three.jsExisting fluency. Declarative scene graph maps cleanly onto an editor's object list.

Where Rust actually shows up

Very little of this app is Rust, by design. The Rust side is plumbing the browser cannot do on its own:

  • Reading and writing the scene file to disk
  • Importing texture files from the filesystem
  • Writing exported PNGs out
  • Native file dialogs and window configuration

Everything else — the scene graph, the editing, the rendering — is TypeScript. Expect to write #[tauri::command] functions and little else.

03Geometry strategy

The decision that constrains everything downstream.

Primitives plus grouping gets you a surprising distance, but it hits a ceiling fast. A bridge built from a box and a cylinder can only ever have a round arch. A pointed or boxed arch needs something more.

Three layers, in order of escalation

LayerHandlesCost
Primitives
+ groups		The bulk of a scene. Walls, posts, crates, slabs, steps. Compound objects via parented groups.Free — built into Three.js, material groups per face included.
CSG
booleans		Cut-outs: doorways, windows, notches, boxed arches. Subtract a box from a box, intersect two cylinders.One library (three-bvh-csg), geometry must be regenerated on edit.
Profile
extrude / lathe		Custom cross-sections. Edit a 2D outline, push it through space or spin it. Arches of any curve, ramps, mouldings, railings.A small 2D profile editor UI. Much cheaper than a 3D mesh editor.
Ruled out

Metaballs — implicit surfaces blend smoothly by nature, which is structurally wrong for architecture where hard edges are the point. Full vertex/edge mesh editing — needs a half-edge data structure, selection modes, extrude/bevel/inset algorithms, and vertex-level undo. That is rebuilding Blender's mesh mode, which is the thing this tool exists to avoid.

Why this matters now

Each layer changes how geometry is produced. Primitives are static and have free per-face material groups; CSG and extrude geometry is generated and must be rebuilt on edit, with material groups tracked by hand. Building the data model around all three from day one means later phases fill in branches rather than refactoring the format.

04Data model

Defined in src/types/scene.ts. This is also the on-disk format.

The key move is GeometrySpec — a discriminated union covering every geometry source the app will ever have. Only primitive and group are implemented; the rest exist in the type so the store, the file format, and the renderer are already shaped around them.

// every way an object can get its shape
type GeometrySpec =
  | { kind: "primitive"; primitive: PrimitiveKind; params }
  | { kind: "extrude";   profile: Vec2[]; depth; bevel…; holes }
  | { kind: "lathe";     profile: Vec2[]; segments; phiLength }
  | { kind: "csg";       op: BooleanOp; aId; bId }
  | { kind: "group" };

interface SceneObject {
  id; name;
  parentId;                 // null = root level
  transform;                // position / rotation / scale
  geometry: GeometrySpec;
  materials: Record<number, FaceMaterial>;   // keyed by group index
  visible; locked;
}

interface FaceMaterial {
  textureId; color;
  tiling; offset; rotation; // UV transform, per face
  doubleSided;
}

interface CameraHotspot { id; name; position; target; fov }

Why materials are keyed by group index

A Three.js BoxGeometry ships with six material groups, one per face. CylinderGeometry has three (side, top cap, bottom cap). Per-face texturing is therefore native — assign a different material to each slot and you are done, no UV unwrapping. PRIMITIVE_GROUP_COUNT records how many slots each primitive exposes.

One document, several view stores

sceneStore holds the document — objects, hotspots, textures — and it is the only thing undo/redo snapshots. Pressing Ctrl+Z must never flip your gizmo back to rotate mode or move the file on disk.

Everything else is split out by what it is for, and none of it is saved: editorStore (selection, gizmo mode, snapping, units, ruler toggles), documentStore (the file path, and whether IO is in flight), cameraStore (projection mode and queued camera moves), viewStore (measurements read back out of the live view), nodeStore (live Three objects by id) and historyStore (the stacks themselves).

Scene file

A JSON document: { format, version, name, objects, hotspots, textures }. Versioned from the start so old scenes can be migrated rather than broken.

06Performance rules

Stability was a hard requirement, so these are rules rather than suggestions.

1. On-demand rendering

The canvas runs frameloop="demand". It renders when something changes — a store update, an orbit drag — not sixty times a second into a static scene. For an editor that sits idle while you think, this is the difference between a quiet machine and a hot one.

Watch for

Anything that animates outside React's render cycle has to request frames itself by calling invalidate(). The transform gizmo is the first case of this; camera hotspot transitions would be another if they ever get animated.

2. Dispose everything

Every geometry and material is disposed in a cleanup effect when it is replaced or unmounted. Without this, editing a primitive's parameters repeatedly leaks GPU memory until the app dies. This is the classic Three.js editor crash.

Watch for

Any new code path that constructs a BufferGeometry, Material, or Texture needs a matching .dispose(). CSG and extrude in phase 04 regenerate geometry on every parameter change, so this gets more important, not less.

3. Memoise on the right dependencies

Geometry is memoised on the geometry spec alone, not the whole object. Moving an object updates a matrix; it must never rebuild a mesh.

4. Keep the stores flat

Objects live in a flat array with parentId references rather than nested children. Serialization stays trivial, and a deep edit does not invalidate an entire subtree of React components.

5. Debounce generated geometry

From phase 04 onward, dragging a slider that drives a boolean or an extrude should debounce the rebuild. Scrubbing a value at sixty rebuilds per second will stall the main thread.
