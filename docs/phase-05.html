01The camera rig

src/components/CameraRig.tsx owns the camera; cameraStore owns the requests.

The camera lives inside the Canvas, so the store cannot hold it. It holds requests instead: a button or a keypress queues one, and the rig applies it on the next frame, where the live camera and orbit controls are in hand.

type CameraRequest =
  | { kind: "view"; view: ViewName; nonce }   // snap, keeping distance
  | { kind: "flip"; nonce }                   // read camera, then invert
  | { kind: "pose"; position; target; fov; nonce }  // absolute
Why a union, and why a nonce

These are three different operations, not three settings on one. Snapping preserves your zoom; flipping has to read the camera before it knows where to go; a hotspot sets an absolute pose and keeps nothing.

The nonce is what makes a repeat request work. Asking for "front" twice running is a real thing to do — orbit away, press 1 again — and a plain value would look unchanged to React.

Surviving a projection swap

Switching between perspective and orthographic replaces the camera object, and OrbitControls rebuilds itself around the new one with its target back at the origin. The old position and target are remembered on every quiet frame and re-applied afterwards.

Why the restore runs in useFrame

Not in an effect. A frame callback is handed live state, so state.camera is definitely the new camera — whereas an effect would depend on the order sibling effects happen to run in, and a hook value read during that render is still the old one. It re-applies for two frames, because there is no guarantee state.controls points at the finished new OrbitControls on the first.

02Axis views

Blender's layout, because that is the one already in muscle memory.

KeyDoes
1 / 3 / 7Front / Right / Top
Ctrl + 1 / 3 / 7Back / Left / Bottom
9Flip to the opposite side
5Perspective / orthographic

Bound on event.code, not event.key: with Num Lock off the numpad reports its keys as Home, End and PageUp, so key would miss them entirely. The number row is bound to the same views, since plenty of keyboards have no numpad at all.

Flip reads the camera

Rather than remembering which button was pressed last — which goes stale the moment the user orbits by hand — nearestView works out which axis the camera is actually closest to, and the flip inverts that. Ties resolve in a fixed order so a perfect diagonal is deterministic.

Snapping preserves distance and target

A view is applied as target plus direction times the current distance, so pressing 1 does not also change how far out you were zoomed, and it works on whatever you have panned over to instead of yanking the camera home.

The pole problem

A top view looks straight along the camera's own up axis, where lookAt has no way to orient the roll and the view collapses. The obvious fix is to swap camera.up to Z — but OrbitControls uses that as its polar axis, so changing it makes every subsequent orbit feel rotated.

The camera is nudged a thousandth of its distance off the pole instead. lookAt stays well conditioned, orbiting stays sane, and it lands the plan view the right way round for free: with up still Y, a camera just past +Y puts world +X at screen right and world +Z down the screen, which is how a floor plan reads.

03Orthographic

Not a side feature — it is what makes an axis view worth having.

Under perspective, a "front view" still converges: parallel edges on the far side of a wall tilt toward a vanishing point. That is exactly what you do not want to trace. A parallel projection makes a front view a true elevation and a top view a true plan.

Two things fall out of it

  • The edge rulers become exact. A parallel projection has one scale at every depth, so the strip drops its "scale at 8.4 m depth" caveat and reads "exact at any depth" instead.
  • Framing carries across the switch. The orthographic zoom is seeded from what the perspective view was measuring at its focus plane, so toggling does not jump.

The near plane is negative, so geometry between the camera and its target is never clipped — in an axis view the camera often ends up inside the bounds of what you are drawing.

04Saved angles

HotspotPanel in the lower third of the left panel.

The data model needed no work. CameraHotspot, SceneFile.hotspots and the history snapshot shape were all laid down in phase 01, and the phase 06 loader already validated them. So saved angles round-trip through a .playstage file and undo like any other edit, for free.

  • + Save captures wherever the camera is now
  • Click a row to restore that angle
  • ⟲ Recapture replaces the pose, keeping the name
  • Active row expands to a name field and a field-of-view control
Capture is a read, not a subscription

The live camera pose is published to viewStore by ViewportProbe on each rendered frame, and the panel reads it with getState() at the moment of the click. Subscribing would re-render the panel continuously through an orbit for nothing.

makeHotspot copies the vectors rather than storing the references it was handed, so a saved angle can never start tracking the live camera.

Field of view

Stored per hotspot and clamped to 10–120 degrees. Below 10 is a telephoto so flat it stops reading as a space; above 120 bends straight edges hard enough to be useless as a reference. Those bounds are shared with the scene loader, so a hand-edited file and a typed value cannot disagree about what counts as a usable lens.

Panel layout

The left sidebar is split 70/30 by flex weight rather than fixed heights, so both halves work at any window size and each scrolls independently. min-h-0 on both is what actually makes that happen — without it a flex child refuses to shrink below its content, the overflow never engages, and the panel grows past the window.

05Known limits

Deliberate, and cheap to lift later.

  • —Projection is not stored per hotspot. Restoring an angle while in orthographic keeps you orthographic. Storing it would take the scene format to version 2, which the loader already handles cleanly — it was just not worth bundling into this chunk.
  • —No shortcut keys for jumping to a saved angle.
  • —No viewport markers showing where saved angles sit in the scene.
  • —No aspect-ratio guides. Framing to a panel shape is still by eye.
  • —Transitions are instant, not animated. Animating one would need invalidate() driving it, per the roadmap's on-demand rendering rule.
  • —The 70/30 split is fixed, not draggable.
