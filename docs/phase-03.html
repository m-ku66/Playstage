01The loading pipeline

A third Rust command, then a cache that lives outside the document.

Texture import is the first thing in Playstage that needs binary data across the IPC boundary. read_image_file joins the two text commands in src-tauri/src/lib.rs, scoped just as narrowly: one path, which the user either picked in a native dialog or which arrived in a scene file they opened. No directory listing, nothing to walk outward from.

fn read_image_file(path: String) -> Result<tauri::ipc::Response, String>
Why Response and not Vec<u8>

A Vec<u8> return crosses IPC as a JSON array of decimal numbers — roughly four characters per byte, parsed one at a time. A 4 MB PNG becomes a 16 MB string and a visible stall. tauri::ipc::Response sends the bytes raw and the frontend receives an ArrayBuffer.

An extension whitelist and a 32 MB cap are enforced in Rust rather than left to the dialog's filter. The filter is a convenience for the user, not a guarantee, and a path can also arrive from a scene file written on another machine.

Decoding

Bytes become a Blob, a short-lived object URL, and an HTMLImageElement. The URL is revoked the moment the element loads; the element keeps its own decoded copy, so revoking does not invalidate the texture.

Why not createImageBitmap

Bitmaps decode off the main thread, which is strictly better — except that the imageOrientation option needed to make their vertical flip agree with Three's default is unevenly supported across the webviews Tauri sits on (WebView2, WKWebView, WebKitGTK). Texture import is a handful of user-initiated loads, not a per-frame cost, so working everywhere beat shaving milliseconds off an action that happens twice a scene.

The document holds paths, nothing else

TextureAsset is { id, name, path }. The decoded image and its THREE.Texture live in textureStore, beside nodeStore, outside the document entirely.

Why a live resource cannot live in the document

The document is deep-frozen in dev, snapshotted by undo, and serialised verbatim to JSON. None of those three things can be done to a GPU resource or an object URL. The original TextureAsset carried a dataUrl field; it was removed, because a blob URL stored there would be written to disk as a dead blob: string and restored by undo after being revoked.

Dropping it had a second payoff: the asset became pure serialisable data, so save and load needed no new code at all. toSceneFile → parseSceneFile → loadScene → useTextureSync already worked end to end.

Paths are references, not copies, so a scene moved to another machine reports its textures as missing rather than silently drawing grey. Making scenes portable stays phase 06's texture-packing job, which will add an explicit embedded field and a format version bump.

useTextureSync

One effect at the app root keeps the cache in step with sceneStore.textures. A hook rather than a subscription inside the store, so the cache stays unaware of the document — the dependency runs one way.

This is also what makes undo free its memory. Undoing an import restores a textures array without the asset, sync sees an entry whose asset is gone, and the image is disposed instead of lingering for the session.

02One master, many clones

The constraint that shaped the whole material layer.

repeat, offset, rotation and center are properties of the Texture, not of the material. Two faces showing the same brick at different tilings therefore need two Texture objects — and FaceMaterial carries tiling per slot by design.

So each cache entry holds one master texture, and every material slot uses master.clone().

Why clones are nearly free

clone() shares the source — the object that owns the uploaded image — and Three ref-counts WebGL textures per source. Fifty clones of one brick are fifty small JS objects and exactly one upload to the GPU. Without the shared source this would be fifty uploads, which is how a texture system eats a graphics card.

Never set needsUpdate on a clone

Its setter marks the source dirty, which would force a re-upload of the shared image for every clone and throw away the entire point of sharing it. The master already flagged the upload. A clone only needs its own transform, and that reaches the shader through the matrix uniform, which updates on its own.

Disposal splits along the same line

Whoever makes a clone disposes it — SceneObjectView's cleanup effect, which also has to do it by hand, because Material.dispose() does not touch the textures a material references. The master is disposed only when the asset leaves the document, and the source ref count means doing so while clones are still mounted cannot pull the image out from under them.

What the store does not set

sRGB colour space, repeat wrapping and trilinear mipmapping are set on the master. Anisotropy is not: its useful maximum is a property of the renderer, which the store has no access to by design, so it is applied per clone in the viewport and capped at 8. Returns diminish sharply past that while bandwidth cost does not, and a modern card reports 16.

03The asset tray

TextureTray, a collapsible strip under the viewport.

Horizontal rather than a panel column, because a texture is recognised by its picture and a row of pictures scans faster than a list of names. Under the viewport rather than in a side panel so the thumbnails can be big enough to tell brick from cobblestone at a glance, which is the whole job of the thing. That costs viewport height, which is why it collapses.

  • Import… opens a multi-select native dialog — wall, road and roof in one go is the normal case
  • Click a tile to apply it to the selection immediately; there is no assign button and no mode to enter
  • The highlighted tile grows rename, Clear and Remove controls
  • Missing files show a lost tile, a count badge in the header, and Retry

Thumbnails are small data URLs generated at decode time, kept in the cache rather than the document. An HTMLImageElement is a single live DOM node and cannot be mounted in two tiles, and re-deriving one per tile per render would cost more than carrying a few kilobytes of PNG.

Assignment walks subtrees

A viewport click on a grouped object selects the group, and a group has no material slots of its own. If setMaterialMany stopped at the selection, clicking a wall of a grouped building and picking a texture would appear to do nothing at all. It expands through subtrees and skips the groups themselves.

Reaching one face of a grouped object is what the outliner and the per-face controls are for.

A silent no-op is a bug report waiting to happen

Clicking a tile with nothing selected did nothing and said nothing, which reads as the feature being broken rather than as a missing selection. The header now says "select an object to apply" or "applies to 3 selected", and tiles dim when a click cannot land. Found within fifteen minutes of first use.

04Per-face materials

MaterialPanel in the inspector. Per-face texturing with no unwrapping.

Three's BoxGeometry already ships six material groups, one per face; CylinderGeometry has three. Per-face texturing is therefore native — the missing piece was never UVs, it was a way to say which face you mean.

PrimitiveSlots
BoxRight · Left · Top · Bottom · Front · Back
CylinderSide · Top · Bottom
ConeSide · Base
Sphere, PlaneSurface

The names are camera-relative on purpose. +x and +z are correct and require translating from the axis gizmo every single time; "Right" and "Front" are what someone placing a texture is already thinking. Generated geometry gets numbered placeholders until phase 04 tracks what its groups correspond to — a numbered slot is honest about not knowing, where a guessed direction would not be.

Hovering a chip lights the face

This is what makes the chips trustworthy: it is how you confirm "Back" means the face you think it does. It also works when the face points away from the camera, which is precisely where clicking the face in the viewport cannot help.

How one face gets highlighted

The geometry is drawn a second time with a material array where every slot but one is visible: false — Three skips those groups entirely. Two module-level singleton materials shared by every highlight, deliberately never disposed: the dispose-everything rule exists because per-object allocations accumulate, and these are two materials for the lifetime of the app.

The alternative — tinting copies of the real materials — would dispose and rebuild an object's entire material set on every hover.

Per slot

Texture, colour (which multiplies the texture, so it doubles as a tint), tiling X/Y, Flip X/Y, offset X/Y, rotation about the face centre, draw-both-sides, and Copy this face to all faces.

Magnitude and direction are separate controls

The tiling fields carry magnitude; the Flip buttons carry sign. A signed -3 sitting in a number box reads as a typo rather than as a mirror, and splitting them means the two controls cannot disagree.

Where the logic lives

src/scene/materials.ts holds it as pure functions over scene data, matching hierarchy.ts and selection.ts. The store is left holding only the decision of when to call it and what to record on the undo stack.

Returning the same reference matters twice

Every function returns the identical array when nothing changed. History snapshots share structure with the live document, and the store decides whether an edit happened at all by reference equality — so a helper that returned a fresh array after changing nothing would spend a Ctrl+Z press on a no-op. Three harness cases pin this down.

verify-materials.mjs is the tenth harness, 25 cases. One of them iterates PRIMITIVE_GROUP_COUNT and asserts the label count matches, so adding a primitive in phase 04 and forgetting its slot names fails immediately rather than shipping a panel with a missing chip.

05Planned: inset textures

A sign on a wall. Not built yet — this is the design.

Today a texture always covers its whole face. The wanted behaviour is a decal: the image occupies a sub-rectangle of the face, with flat colour around it. A poster, a sign, a window.

Why the naive version looks broken

Clamped wrapping plus a scaled UV transform places the image in a sub-rectangle perfectly well — and then fills the area around it with the image's edge pixels, smeared outward. That smear, not the placement, is the actual problem to solve.

The approach

Patch one line of MeshStandardMaterial's fragment shader through onBeforeCompile, replacing #include <map_fragment> with a version that only multiplies the texture in when the UV falls inside [0,1]:

// outside the window, diffuseColor is left as the material colour
if ( uv.x >= 0.0 && uv.x <= 1.0 && uv.y >= 0.0 && uv.y <= 1.0 ) {
  diffuseColor *= texture2D( map, uv );
}

That gives a genuine flat surround, on any geometry, with no second mesh and no extra GPU upload. Clone sharing survives intact.

What makes it safe rather than clever

  • customProgramCacheKey, so Three does not hand inset and non-inset materials the same compiled program.
  • Graceful degradation. If that shader chunk is ever renamed in a Three upgrade, the string replace misses and the face renders full-cover instead of throwing.

Data model

FaceMaterial gains inset: { x, y, width, height } | null, with null meaning cover — today's behaviour, so every existing scene is unaffected and no version bump is needed.

Inset and tiling become mutually exclusive: inside a window the image is placed once. The tiling fields grey out with a note rather than letting two controls quietly fight over the same UV transform.

The part that cannot be tested

The data model, the parsing and the round trip are all harness-testable. Whether the surround actually reads as flat colour is not — tsc and Node cannot run a shader. That one needs an eyeball.

06Known limits and open bugs

What is outstanding, and one live regression.

OPEN BUG — Ctrl+S does not fire, Ctrl+Z is unreliable

The toolbar Save button works, and the save path is proven: a fully textured document with negative tiling and a Windows path serialises and round-trips correctly. So saveScene() is sound and simply is not being reached from the keyboard.

Every stopPropagation in src was audited — all seven in the Outliner are on click and drag, AddMenu's capture listener only touches Escape, and NumberField's onKeyDown only blurs on Enter. Nothing in the code eats the key.

The document and history shortcuts were moved to a capture-phase listener on window as a result. That did not fix the symptom, but it is the right structure regardless: the main handler is bubble-phase on window, and React attaches its listeners at the root container below window, so one stopPropagation anywhere could silently kill every global shortcut while that element held focus.

Next suspect: WebView2 consuming the accelerator before the page sees it, which is a Rust-side setting rather than anything in the frontend. That Ctrl+Z is also affected points the same way — the common factor is the modifier, not the letter.

  • —No viewport face picking. Clicking a face to target its slot is not wired up. intersection.face.materialIndex hands it over for free, so this is a targeting mode rather than new maths.
  • —No material presets. A named FaceMaterial reusable across a scene, as the roadmap lists.
  • —No flat-colour or wireframe render modes for clean draw-over references. View state, so editorStore rather than the document.
  • —No inset textures. Designed above, not built.
  • —No real-world scale lock. Tiling is in UV repeats, so a brick texture stretches when the wall does. Deriving tiling from the face's world dimensions was considered and deferred.
  • —The texture dropdown is a native select, so it renders with OS chrome that does not match the rest of the panel. Functional, slightly off-key.
  • —No drag-and-drop import. Native file-drop is disabled app-wide, so the dialog is the only way in.
  • —No texture packing, so a scene is not portable between machines. Phase 06.
