02Gizmos

How the handles attach, and how their output gets back into the document.

Each SceneObjectView renders its own TransformControls when it is the selected object. The gizmo attaches to that object's group via the object prop rather than wrapping it as a child, so the group's transform stays driven by the store in the normal way.

Why the gizmo is 3D and not a 2D overlay

The handles live in the scene rather than being drawn over it. That sounds like it should cause collisions, but TransformControls isolates itself: its materials run with depthTest and depthWrite off at a high render order so nothing can occlude them, and it raycasts with its own raycaster against invisible oversized picker volumes, separate from R3F's event system. Grabbing a handle never falls through to the mesh behind it.

The argument for 3D is that the drag maths is 3D regardless — translating along an axis under perspective means intersecting the pointer ray with a plane containing that axis. A 2D overlay would still need all of that, plus hand-rolled projection to place the handles each frame, and would lose correct foreshortening on axis arrows and near/far arcs on rotation rings. 2D is the right tool for information layered on the gizmo (live numeric readouts, axis labels) rather than for the handles themselves.

Export gotcha

The gizmo is in the scene graph, so a naive render-to-PNG in phase 06 would bake blue arrows into the exported frame. Hide or detach it before the export render pass.

The callback-ref trick

A plain useRef would still be null on the render where the gizmo wants to mount — refs populate after commit, and nothing triggers a second render. Storing the node in state via a callback ref forces that extra render:

const [node, setNode] = useState<THREE.Group | null>(null);

<group ref={setNode} position={…} rotation={…} scale={…}>…</group>

{isSelected && node && (
  <TransformControls object={node} mode={transformMode} … />
)}

Committing back to the store

The gizmo mutates the Object3D directly, outside React. onObjectChange reads that live state back into the scene store, which keeps the properties panel's numbers in sync while you drag.

frameloop demand

Because the canvas only renders on demand, a gizmo drag would otherwise freeze mid-motion — the mutation happens outside the render cycle, so nothing asks for a frame. commitTransform calls invalidate() explicitly. Any future out-of-React animation needs the same.

Orbit handoff

OrbitControls is marked makeDefault, which lets TransformControls find and suspend it while a handle is being dragged. On top of that, isDragging in the editor store gates two things: orbit is explicitly disabled mid-drag, and onPointerMissed refuses to clear the selection when a drag happens to end over empty space — otherwise letting go of a handle in the wrong spot would deselect the thing you were just moving.

03Snapping

On by default, because architectural blocking wants alignment more than freedom.

AxisDefaultNotes
translate0.25 unitsQuarter-metre grid. Editable from the toolbar.
rotate15°Stored in degrees, converted to radians at the gizmo.
scale0.1Multiplier step.

All three are gated behind one snapEnabled switch, toggled from the toolbar or with X. When off, the gizmo's snap props are passed as null, which is what Three.js expects for "no snapping" — passing 0 would snap everything to the origin.

One global listener, installed once in App.

The handler reads both stores through getState() rather than subscribing. That keeps it to a single listener for the lifetime of the app instead of tearing down and rebinding every time the selection changes.

Bare-letter shortcuts bail out when the event target is an input, textarea, select, or contenteditable — otherwise typing "Wrecked wall" in the name field would flip gizmo modes three times. Undo and redo deliberately stay live even in a field: in an editor like this, Ctrl+Z means "undo my last edit to the scene", not "undo my last keystroke in this box", and the coalescing described below already makes field typing a single history entry.

05The store split

Why selection moved out of the scene store.

Phase 01 kept selectedId in sceneStore alongside the objects. That was fine until undo entered the picture. Undo snapshots the document — and if selection lives in the document, Ctrl+Z starts re-selecting whatever was selected three edits ago. Same for gizmo mode and snap settings.

StoreHoldsSaved?Undoable?
sceneStoreobjects, hotspots, textures, name, dirty flagYesYes
editorStoreselection, gizmo mode, snap settings, drag stateNoNo
historyStorepast / future stacks, batch and coalesce bookkeepingNo—

A few scene actions still need to touch selection — deleting the selected object should clear it, adding one should select it. Those reach across with useEditorStore.getState() rather than returning a value for the caller to act on, which keeps call sites simple.

06Undo / redo

Snapshot history, 100 entries deep, with batching and coalescing so one gesture is one step.

Snapshots, not diffs

Each entry is a shallow copy of the document's four fields: name, objects, hotspots, textures. No deep cloning. That is safe because every mutating action builds new arrays and objects rather than editing in place — objects.map(o => o.id === id ? {...o, …} : o) and friends. An old snapshot can never be changed out from under the stack.

It is also why the memory cost is negligible: in a hundred-object scene, moving one box produces a snapshot that shares ninety-nine object references with the previous one. Only the array and the single changed object are new.

The rule this depends on

Never mutate a SceneObject in place — meaning never write obj.name = "Wall"; always build a replacement with { ...obj, name: "Wall" }. This is about how the code writes a change, not about what the user can edit; it constrains no feature.

An in-place write reaches through every history entry holding a reference to that object and rewrites what those entries remember. The symptom is "undo doesn't work sometimes", which points nowhere near the cause.

Enforcing it instead of trusting it

A convention you can break by accident, whose failure mode is silent, is worth making loud. devFreeze.ts deep-freezes the document after every state change, so an in-place write throws a TypeError at the offending line rather than quietly corrupting the past. It is gated on import.meta.env.DEV and stripped from production builds.

Children are frozen before their parents, which establishes "frozen parent implies frozen descendants". That lets the walk return early on anything already frozen, so the cost rides on structural sharing rather than fighting it: after editing one object in a hundred-object scene, the walk visits the new array and the one new object, and bounces off the other ninety-nine in a single check each.

PatternUnder freeze
obj.name = xThrows — this is the point
obj.transform.position[0] = xThrows — freezing is deep
objects.push(…)Throws — arrays are frozen too
map + spreadFine
[...objects, next]Fine
filterFine
structuredCloneFine — the copy is mutable

Only the document slice is frozen. Editor state is never snapshotted, so mutating it cannot corrupt anything and it is left alone.

Dependency direction

historyStore is a dumb container — it holds past, future, and the bookkeeping fields, with no actions at all. Everything that pushes, pops and applies snapshots lives in sceneStore and drives history through setState. Keeping it one-directional (sceneStore → historyStore) avoids a circular import, since history needs to write back into the scene to time-travel.

Batching: one drag, one entry

A gizmo drag fires onObjectChange on every mouse move, each of which writes to the store. Without intervention that is sixty undo steps per second.

beginBatch(key) records the pre-drag snapshot and then closes a gate; while batchKey is set, record() returns immediately. endBatch() reopens it. The gizmo calls these from onMouseDown and onMouseUp.

Ordering matters

On mouse-up, the final commitTransform() has to run before endBatch(). Reverse them and that last write lands outside the batch and shows up as a spurious second undo entry — so undoing a drag would take two presses, with the first appearing to do nothing.

Coalescing: one gesture, one entry

Typing a name or nudging an inspector number has no mouse-down/up pair to hook, so those use a time window instead. record() takes a key and a coalesce flag; repeated edits with the same key inside 600ms refresh the timestamp rather than pushing a new entry. Keys are scoped per object (rename:<id>, transform:<id>) so editing two objects in quick succession stays two steps.

Other details

  • Any new edit clears the future stack — standard linear-history behaviour, no branching.
  • Time-travelling prunes the selection if the selected object does not exist in the restored snapshot.
  • newScene and loadScene wipe history entirely — you should not be able to undo across a file boundary back into the previous document.
  • Undo and redo both refuse to run mid-batch, so a drag cannot be interrupted halfway.
  • Undo sets the dirty flag. The document differs from what is on disk either way.
  • The dev freeze guard above is what keeps the reference-sharing honest as new actions get written.

07Grouping

Nesting in the scene graph, a tree outliner, and reparenting that does not move anything.

World-preserving reparent

Dragging an object into a group does not move it. Its world transform is held fixed and the difference is baked into a new local transform:

newLocal = inverse(parentWorld) × currentWorld

The alternative — keeping the local transform and letting the object jump to wherever that lands relative to its new parent — is almost never what anyone wants. By the time you are grouping things, you have already placed them.

The maths runs off the store's flat object list, not the live Three.js scene graph, walking the parentId chain to compose world matrices. The store is the source of truth; the scene graph is a projection of it, and a reparent happens inside a store action before the renderer has caught up.

Verified, not assumed

scripts/verify-transforms.mjs asserts the world matrix is identical before and after reparenting, across translated, rotated, scaled and fully-composed parents, into groups, out of groups, between groups, and through a four-deep chain. It also covers the refusal cases. Run it with node scripts/verify-transforms.mjs after touching the maths.

Known limitation

Decomposing a matrix back into position / Euler / scale cannot represent shear. Parent a rotated object under a non-uniformly scaled group and the result is the closest shear-free approximation, not an exact match — so it can shift slightly. Three.js has the same limitation anywhere it decomposes. Avoiding non-uniform scale on groups sidesteps it entirely; a later fix would be storing a raw matrix on the object instead of a TRS triple.

Cycles

canReparent refuses self-parenting and refuses any target that is already a descendant of the object being moved. The outliner calls the same function to decide whether a row is a legal drop target, so the UI never offers a drop the store would silently reject. World-matrix composition also carries a seen set, so a cycle arriving from a hand-edited scene file cannot hang the app.

Why the gizmo moved to the scene root

Previously each object rendered its own TransformControls. That breaks the moment objects nest: a gizmo mounted inside a group inherits that group's matrix, so a child of a 0.2-scaled group gets handles a fifth of their intended size, rotated and offset along with the parent.

The gizmo is now a single SelectionGizmo at the root of the scene. It finds its target through nodeStore, a registry of live Three objects keyed by scene object id, which each SceneObjectView writes itself into on mount. Handles stay in world space; the values written back are still local, because that is what TransformControls mutates and Three handles the parent matrices.

Three stores, three lifetimes

nodeStore holds live mutable Three objects and is deliberately separate from the document. It is never saved, never snapshotted, and never frozen — it is a view-layer index, not state.

Rendering and the outliner

  • The viewport renders root objects only; each SceneObjectView recurses into its own children, so a parent's matrix cascades for free
  • Hiding a parent returns null and takes the whole subtree with it
  • A group is a transform container with no mesh — geometry.kind === "group" skips geometry entirely, and a selected empty group shows an axes marker at its origin since it has nothing to outline
  • Outliner rows are draggable; drop on a row to nest, drop on the empty list area to move back to the top level
  • Drop targets are validated on hover rather than only on drop, which needs the dragged id in React state — dragover cannot read DataTransfer contents for security reasons
Tauri on Windows swallows HTML5 drag

Outliner dragging silently does nothing until dragDropEnabled is set to false on the window in tauri.conf.json. It defaults to true, which hands drag events to the native OS file-drop handler before the webview sees them — so dragstart never fires in the page. Tauri's own docs call this out: disabling it is required to use HTML5 drag and drop on Windows.

The trade is that the app no longer receives native file-drop events. When texture import lands in phase 03, a dropped-file path will need a file dialog or a Rust-side listener rather than a webview drop target.

user-select: none blocks drag too

A second, independent cause of the same symptom. Chromium will not start a drag on content inside a user-select: none subtree even when draggable="true" is set, and the app body sets exactly that to stop text selection during orbiting. [draggable="true"] { -webkit-user-drag: element; } in styles.css opts those elements back in.

MVP shape

Creating a group adds an empty one, then you drag objects onto it. The more natural "select three things and hit Group" needs multi-select, which does not exist yet. Worth adding, but it is its own chunk.

08Primitive parameters

Editing a shape's own numbers — radius, height, segment counts — rather than only its transform.

One spec table, not five panels

PRIMITIVE_PARAMS in scene.ts is now the single source of truth. Each entry carries a label, a default, a clamp range, an input step, and whether the value must be a whole number. PRIMITIVE_DEFAULTS is derived from it rather than maintained alongside it, and the inspector renders its fields by iterating the specs.

The practical effect is that adding a torus later means adding one block to that table. No new panel, no new defaults entry, no inspector change.

Clamping, and where it lives

KindRangeWhy
dimensions0.01 – 1000Zero-size geometry renders as nothing and is hard to recover from in the viewport.
cylinder radii0 – 1000Zero is legitimate here — it collapses one end to a point, which is a cone.
segment counts3 – 128, integerPast this there is no visible improvement at the scale this tool draws at, and a stray keystroke asking for 50,000 would hang the renderer building the buffers.

Clamping happens in the store action, not only in the input. A value can also arrive from a loaded scene file or, later, a script; the renderer should not be reachable by any path that has not been bounded.

A number input that does not fight you

Binding an input straight to clamped store state breaks the moment someone clears the field to retype. The empty string parses as zero, zero clamps to the minimum, and the field snaps to "0.01" mid-keystroke. Typing a leading "-" or a lone "." does the same.

NumberField keeps its own draft string. Edits commit upward whenever the draft parses to a finite number, but the displayed text stays exactly what was typed until focus leaves — at which point it resyncs from the store, which is how a clamp becomes visible rather than disruptive. External changes (a gizmo drag, an undo) update the field too, but never while it is focused.

The transform vector inputs now use the same component, so the behaviour is consistent across the panel.

Rebuild cost

Changing a parameter produces a new geometry spec object, which invalidates the geometry memo, builds a replacement, and disposes the old one. That is the dispose discipline from phase 01 doing its job for the first time under real churn.

Materials were being rebuilt alongside it for no reason, since their memo depended on the whole geometry spec. They now depend on the material slot count, which only changes when the primitive kind does — so editing a radius no longer disposes and recreates six box materials per keystroke.

Still fine, but watch it later

Primitive geometry is cheap enough to rebuild per keystroke. Generated geometry in phase 04 is not: a boolean or an extrude rebuilt sixty times a second while scrubbing a slider will stall the main thread. That is where debouncing becomes mandatory rather than optional.

Verified, not assumed

Nothing in the type system ties PRIMITIVE_PARAMS to the p.width / p.radialSegments reads in buildGeometry.ts — the params bag is Record<string, number>, so a rename on one side yields undefined on the other, then NaN vertices and an object that silently fails to draw. scripts/verify-params.mjs reads both source files, compares the names it finds in each, and then builds every primitive at its defaults, minimums and maximums checking for NaN. Run it with node scripts/verify-params.mjs.

09Outliner polish

A bug found in testing, plus the two deferred items it made sense to pick up alongside the fix.

Bug: duplicating a group lost its contents

duplicateObject copied exactly one object. For a box that is correct; for a group it produced an empty shell, because the children still referenced the original group's id and so stayed where they were.

The fix collects the whole subtree, mints a fresh id for every object in it, and remaps internal parentId links onto the new ids so the copy is self-contained. The root copy keeps the source's own parent, so a duplicated group lands beside the one it came from rather than jumping to the top level.

Why this was easy to miss

The flat-list-plus-parentId model makes most operations naturally recursive — delete already cascaded, and rendering nests for free. Duplicate was the one place that had to walk the tree explicitly, and it was written before hierarchy existed at all. Worth asking the same question of anything else predating 2c.

Reordering

An object's index in the flat array decides its order among its siblings. Absolute position is irrelevant — only relative order within a parent matters, since both the renderer and the outliner group by parentId.

setParent is now a thin wrapper over moveObject(id, parentId, beforeId), which reparents and repositions in one step. Only the object itself moves in the array; its descendants stay put, which is harmless because their order relative to each other is unchanged.

Drop targets follow the usual file-tree convention: the middle 40% of a row nests into it, the top and bottom 30% insert before or after it. The intent is recomputed from the pointer's position within the row on every dragover, so the insertion line previews exactly what will happen.

Collapsible groups

A disclosure triangle on any row with children, with the collapsed set living in editorStore — presentation state, never saved and never undone. A collapsed group shows its child count. Starting a drag auto-collapses the dragged group, since dropping something into a child you cannot see would be confusing.

Testing the real source

The earlier harnesses mirror their logic, which tests the copy rather than the code. Node 22 can strip TypeScript types directly, so verify-hierarchy.mjs imports src/scene/hierarchy.ts itself — no copy, no drift. That is why the list operations were pulled out of the store into their own module: a pure function is testable, a store action is not.

19 cases, including a regression test for the duplicate bug by name. npm run verify runs all three harnesses.
